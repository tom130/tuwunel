Purpose

Make native OIDC sign-in actually complete in a Chromium browser when the Matrix client lives on a different origin than the homeserver — the ordinary Element Web deployment. Today 0 of 5 observed sign-in attempts on matrix.datadialect.cz reached the token endpoint; the user is shown a raw JSON M_NOT_FOUND body instead of a session.

Acceptance bar. After this plan: a password sign-in from Element Web in Chrome lands back on the client with ?code=&state= and produces exactly 1 POST /_tuwunel/oidc/token in the ingress log; a failed completion leaves the pending authorization request intact so the next submit succeeds; and no browser-facing OIDC route ever renders a bare Matrix JSON error to a human.

Out of scope. The upstream-IdP (SSO) login path beyond the shared _complete handler; the RFC 8628 device grant; MSC4108 QR login; the appservice/bridge 404 noise visible in the same logs; any change to PKCE, token lifetimes, or the client-registration endpoint.

Problem

Signing in through the built-in login page (oidc_native_auth = true) silently does nothing in Chrome. The password is accepted, the homeserver mints an authorization code and answers 307 toward the client's redirect_uri — and the browser discards that navigation. The user, seeing an unchanged form, submits again; the second attempt reuses the same oidc_req_id, which the first attempt already consumed, so the server answers 404 with the JSON body the user reported.

Two independent defects stack here. The first (D1) is the blocker: a global Content-Security-Policy with form-action 'self' is attached to every HTML response, including the sign-in page, and Chromium enforces form-action against every hop of a form submission's redirect chain — so the cross-origin final hop is refused. The second (D2) turns a recoverable hiccup into a dead end: take_auth_request deletes the pending request before the login token is validated, so any completion that fails for any reason burns the request permanently. A third, smaller defect (D3) is cosmetic but is what the user actually saw: the browser-facing _complete and authorize routes render Matrix JSON errors rather than the styled HTML error page every other OIDC page uses.

Verified live against the running deployment (2026-08-31, kubectl --context OCI + curl):
  • The CSP is real and is ours. GET /_tuwunel/oidc/native?oidc_req_id=… returns content-security-policy: default-src 'none';script-src 'self';style-src 'self';frame-ancestors 'none';form-action 'self';base-uri 'none'. It is emitted by the app, not the ingress: TUWUNEL_CSP at src/router/layers.rs:62-69, applied to every text/html response by html_layer() at src/router/layers.rs:258-279. No ingress annotation sets any CSP.
  • The final hop is cross-origin. Element registers redirect_uri = https://element.datadialect.cz/?no_universal_links=true while the page is served from matrix.datadialect.cz; complete_route answers Redirect::temporary (307) to that URL (src/api/oidc/complete.rs:41-72).
  • The double-submit is systematic. Ingress logs show the identical shape in 5 of 5 attempts, e.g. 20:04:12 POST /native 303 → 20:04:12 GET /_complete?…&loginToken=EUYj… 307 → 20:04:14 POST /native 303 → 20:04:15 GET /_complete?…&loginToken=h7lS… 404. Two different login tokens against one oidc_req_id: the page was submitted twice because the first navigation never happened.
  • The client never gets the code. Across the full 3-hour window there is not a single POST /_tuwunel/oidc/token — and no OPTIONS preflight for it either, though the preflight for /registration is logged. The authorization code issued at 20:04:12 was never redeemed.
  • D2 reproduced directly. Against a throwaway registered client: first GET /_complete?oidc_req_id=Vuhe…&loginToken=bogus… → 403 M_FORBIDDEN: Invalid or expired login token; second, identical request → 404 M_NOT_FOUND: Unknown or expired authorization request — the user's exact error. take_auth_request removes the row at src/service/oauth/server/auth.rs:113-115, before find_from_login_token is ever called.
  • D3 reproduced. GET /_tuwunel/oidc/native?oidc_req_id=zzz&view=login returns 200 and renders a fully functional form bound to a request that does not exist.
  • Not an infrastructure problem. One tuwunel-datadialect pod, 0 restarts, 26 days old — no split RocksDB state, no rollout window.

Solution

Keep the hardened global CSP, but let the pages that exist specifically to hand the browser to a registered OAuth client say so. The native sign-in and registration pages, when bound to an authorization request, emit their own Content-Security-Policy whose form-action lists 'self' plus the origin of that request's already-validated redirect_uri. Nothing else about the policy changes, and no other HTML response is touched — html_layer() uses .entry().or_insert(), so a header set by the handler already wins.

Then remove the trap underneath it: _complete switches from take-then-validate to peek → validate → consume. A bogus oidc_req_id still cannot burn a valid login token (the peek fails first, exactly as the current comment intends), but a failed or blocked completion now leaves the pending request alive, so the very next submit works. Finally, the browser-facing routes get the same styled HTML error page the rest of the OIDC surface uses, with a link that restarts the flow, and the sign-in page refuses to render a form for a request that no longer exists.

Questionables

Is the Chromium form-action-on-redirects behaviour certain enough to build on?

It is the leading explanation, not yet an eyewitnessed one, which is exactly why Phase 0 exists as a gate. The browser-behaviour divergence is documented (Chromium enforces form-action against redirects; Gecko does not), and every server-side observation fits it: a 307 issued and never followed, zero token exchanges across five attempts, a second form POST about two seconds later, and the app-scheme clients that route through the needs_interstitial link — a click, not a form submission — being unaffected. If Phase 0 shows no violation, Phases 2–4 remain valid on their own and Phase 1 is re-scoped.

Scope form-action per request, or simply drop the directive?

Dropping form-action from TUWUNEL_CSP is a two-character fix and would work. It is rejected as the primary approach because it weakens every HTML surface the server has — admin, media, account management — to fix one page, and because form-action is the specific mitigation against a dangling-markup injection retargeting a password form. Per-request scoping costs one helper and one response builder, and the value it inserts is the redirect_uri the server itself validated against the registered client minutes earlier. If review prefers the smaller diff, the fallback is form-action 'self' https: on the OIDC pages only — still narrower than removing the directive.

Can two concurrent completions still race for one authorization request?

In principle yes: peek is not atomic with take, so two simultaneous _complete calls could both peek before either takes. Phase 2 narrows the window by consuming immediately before issuing the code and treating a failed take as "already completed", which means at most one code is issued in practice. Closing it fully needs a compare-and-delete the current Map API does not expose. The residual risk is small — an attacker would need a second valid, unexpired, single-use login token for the same request inside the same few milliseconds — but it should be recorded rather than assumed away.

Should the _complete interstitial simply be used for every client?

It would sidestep the CSP entirely — a link click is not a form submission — and it is already the path for private-use schemes and native https universal links. It is not the primary fix because it adds a mandatory extra click to every web sign-in, which is a permanent UX tax paid to work around a header we control. It stays on the table as a fallback if per-request CSP scoping proves awkward for some client shape.

Is there anything to unblock the user before a rebuild?

Two things. Signing in through Firefox should work today, since it does not apply form-action to redirects — worth confirming in Phase 0 anyway. And an ingress-nginx configuration-snippet using more_set_headers on the /_tuwunel/oidc/ location can overwrite the app's CSP without touching the image; note that snippet annotations are disabled by default in ingress-nginx ≥ 1.9 and would have to be enabled cluster-wide, which is its own security decision. Both are stopgaps, not the fix.

Notes

Phase 0 browser confirmation

On 2026-08-31, an automated two-origin harness replayed the production response shape with the exact live CSP. Chrome 148 submitted once to the same-origin endpoint, received a 307, stayed on the form, and made zero requests to the cross-origin target. Its verbatim console line was:

Sending form data to 'http://127.0.0.1:18081/submit' violates the following Content Security Policy directive: "form-action 'self'". The request has been blocked.

Firefox 151 submitted the identical form and followed the same 307 to the target. A fresh live header probe confirmed that matrix.datadialect.cz still serves the exact tested policy; the four-hour ingress window independently retained the recorded production POST → 307 → second POST → 404 sequences and no token exchange.

How the regression got in

The directive has changed three times, and the current value is newer than the feature it breaks. Native OIDC login shipped on 2026-06-28; the policy that breaks it landed three weeks later in a commit whose subject is Cleanup headers.

The reading this supports: native sign-in with a cross-origin web client has never worked in a Chromium browser. Issues #504 and #505 addressed the redirect construction, one layer below the header that actually blocks it.

Reproduction transcript (2026-08-31, throwaway client BO0Iz6WB…): 
GET  /_tuwunel/oidc/authorize?…            307  → /native?oidc_req_id=Vuhe3C6O…
GET  /_tuwunel/oidc/native?oidc_req_id=…  200  form rendered
GET  /_complete?oidc_req_id=Vuhe…&loginToken=bogus   403  Invalid or expired login token
GET  /_complete?oidc_req_id=Vuhe…&loginToken=bogus   404  Unknown or expired authorization request
The two identical requests differ only in that the first one silently consumed the authorization request. That second line is the error the user reported.

Why the mobile clients were never affected

needs_interstitial in src/api/oidc/complete.rs:82-85 serves a "Continue" page instead of a redirect for private-use schemes and for a native client's https universal link. The user then clicks a link, which starts a fresh navigation that form-action does not govern. So Element X on Android and iOS complete sign-in normally while Element Web on desktop cannot — a divergence worth remembering when triaging any future report of this shape.

Rejected approaches

Remove form-action from TUWUNEL_CSP. Fixes the symptom in one line but relaxes the policy on every HTML response the server emits, including admin and media surfaces, to solve a problem that exists on exactly one page. Kept as a documented fallback, not the plan.
Override the CSP at the ingress. Works without rebuilding and is listed as a stopgap, but it moves a security-relevant application header into cluster configuration where the next person reading layers.rs will not see it, and it depends on snippet annotations being enabled cluster-wide.
Force the interstitial for every client. Sidesteps the CSP correctly but taxes every web sign-in with an extra click, permanently, to route around a header we own.
Make _complete idempotent by retaining the request until expiry. Tempting — it would make the retry work without touching the CSP — but it lets one authorization request mint multiple codes for ten minutes, weakening the single-use property the OAuth code flow depends on. Phase 2's peek → validate → consume gets the recoverability without that cost.

Loose threads worth a separate look

  • Element re-registers a dynamic client on every attempt (six POST /registration in five minutes, all returning the same deterministic client_id). Harmless, but it makes the logs noisy and is worth understanding.
  • Login tokens are single-use — find_from_login_token removes the row on read (src/service/users/mod.rs:536-558) — so a retry always needs a fresh form submission. That is correct, and it is why Phase 2 restores the request rather than the token.
  • The same logs show constant appservice failures (mautrix-discord 404s, mautrix-whatsapp connection refused). Unrelated to login, but they are burying real signal in the pod logs.
  • authorize_route and complete_route are the only two browser-navigation routes that still return Result and therefore JSON; Phase 3 fixes both, and a lint or review note would keep new ones from appearing.
